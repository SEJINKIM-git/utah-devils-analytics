# 2022~2025 재업로드 실행 절차

이 절차는 **승인받은 운영진이 직접** 실행한다. 이 문서는 DB 변경을 실행하지 않는다.

1. PR을 `#3 → #4 → #5(#6 포함)` 순서로 병합하고 Vercel 배포를 확인한다.
2. 병합된 `main`의 SQL을 `001 → 002 → 005 → 006` 순서로 적용한다. 특히 001은 반드시 병합 후 `main` 버전이다.
3. Supabase 스냅샷을 한 번 만든다. `console_audit_log`가 저장 전·후 값을 남기므로 별도 행 단위 백업은 필요 없다.
4. 각 업로드 파일의 `(시즌, 배번, 이름)`을 `sql/review/reupload_precheck.sql`의 JSON 입력에 넣고 실행한다. B 결과(다른 테이블 참조)가 있으면 선수 ID별로 **새 선수로 옮길지, 기존 참조를 유지할지** 결정한다.
5. 콘솔 업로드 미리보기에서 `이름 다름` 건수를 확인한다.
6. `2022 → 2023 → 2024 → 2025(-3 파일)` 순서로 저장한다. 시즌마다 저장 직후 선수 수·타자/투수 요약 행 수를 확인한다.
7. 문제가 생기면 `console_audit_log.before`의 JSON을 검토해 되돌릴 행과 값을 확정한 뒤, 별도 승인 후 SQL Editor에서 복구한다.

## 참조 이동 템플릿 (승인 전 실행 금지)

`reupload_precheck.sql`의 B 결과로 확인한 **실제 FK 테이블·열**만 사용한다. 아래의 ID와 테이블·열은 운영자가 채운다.

```sql
begin;
update public.<실제_참조_테이블>
set <players를_참조하는_열> = <새_player_id>
where <players를_참조하는_열> = <기존_player_id>;
commit;
```

이 SQL은 참조 이동만 위한 템플릿이다. 자동 실행하거나 선수 ID를 추정하지 않는다.
